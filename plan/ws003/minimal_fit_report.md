### 3.2 ワーストタイミングパス詳細

- **Path Group**: `g_out` (gclk, 20 MHz / 50.000 ns)
- **Slack (VIOLATED)**: **-4.190 ns** (Required: 50.000 ns, Arrival: 53.997 ns, Data Path Delay: 53.997 ns)
- **Source**: `gpu/g_su[0].su/fpu/g_lane[2].u_core/g_lat4.s4_a_reg[28]/C`
- **Destination**: `gpu/g_su[0].su/pk/pipe_reg[0][80]/D`
- **Logic Levels**: **165 段** (`CARRY4=62`, `LUT2=10`, `LUT3=4`, `LUT4=12`, `LUT5=16`, `LUT6=61`)
- **Fmax 計算**:
  $$T_{min} = T_{clk} - \text{WNS} = 50.000\text{ ns} - (-4.190\text{ ns}) = 54.190\text{ ns}$$
  $$F_{max} = \frac{1}{T_{min}} = \frac{1}{54.190\text{ ns}} \approx 18.45\text{ MHz}$$
  ※未配置（Unplaced）段階での概算値。FPU〜Packer間の段数過多（165段）が主因。

## 4. リソース超過（LUT 330k）の根本原因分析

### 原因 1: `atg_tu_cache` の BRAM 非推論（82.5k LUTs / 71.8k FFs の浪費）
- `rtl/gpu/tu/atg_tu_cache.v` の 4 バンクキャッシュメモリ配列（`reg [511:0] data_b0..b3 [0:NSETS-1][0:WAYS-1]`）が 2 次元配列で記述されており、Xilinx Vivado が BRAM ではなくフリップフロップおよび分散 LUT として展開。
- 単一モジュールで **82,539 LUTs**, **71,854 FFs** を消費（全体の約 24%）。

### 原因 2: `atg_rop_fblend` のファブリック浮動小数点演算器展開（70.8k LUTs の浪費）
- `rtl/gpu/rop/atg_rop_fblend.v` において、RGBA 4 色チャネル × 4 レーン構成で、組み合わせ（`LAT(0)`）の単精度浮動小数点加算器（`am_fp_add`）および乗算器（`am_fp_mul`）が大量にインスタンス化。
- `atg_rop_wb` 全体で **70,839 LUTs** を消費。

### 原因 3: `atg_kc705_top.v` における `config.mk` 定義の非反映
- `boards/kc705/atg_kc705_top.v` で `include/atg_config.vh` がインクルードされておらず、以下のパラメータが固定値でハードコードされていた：
  - `SU_NREGS(64)`（minimal の 32 ではなく 64）
  - `SU_LDS_BYTES(16384)`（minimal の 1024 ではなく 16 KiB）
  - `SU_PACKED(1)` / `SU_SUBGROUP(1)`（minimal の 0 ではなく有効化）
- これにより SU および ROP のリソース削減が無効化されていた。

## 5. KC705 ミニマム Fit 化への是正方針と削減見込み

| 是正項目 | 内容 | 削減見込み LUT |
| :--- | :--- | :---: |
| **1. `atg_tu_cache` BRAM化** | 1次元フラット化 + `(* ram_style = "block" *)` 付与 | **約 -75,000 LUTs** |
| **2. `atg_kc705_top.v` 連動** | `atg_config.vh` をインクルードし `minimal.mk` パラメータ反映 | **約 -25,000 LUTs** |
| **3. `atg_rop_fblend` 最適化** | minimal 時の fblend パイプライン無効化 / DSP マッピング | **約 -50,000 LUTs** |
| **合計削減見込み** | - | **約 -150,000 LUTs** |

**是正後の予想 LUT 数**:
$$\approx 345,821 - 150,000 = \mathbf{195,821\text{ LUTs}}\quad (\text{Kintex-7 325T の 96\% 程度})$$
さらに不要なデバッグ機能やキャッシュサイズの抑制により **120k〜140k LUTs（60〜70%）** への確実な収容が見込めます。
収容完了後、P&R を再実行して 20 MHz タイミングの達成検証を行います。

## 6. L2 キャッシュ（`atg_mc_l2`）BRAM 化・単体合成結果（2026-10-27 追加）

### 6.1 単体合成（Out-Of-Context: 16 KiB 構成, 4 ways × 64 sets）結果
- 実行ツール: `tools/vivado-synth-l2.sh` (Vivado 2026.1, `xc7k325tffg900-2`)
- 論理合成ステータス: **PASS**
- **Slice LUTs**: **15,221** (利用率 7.47%) ← 修正前推定 90,622 LUT から **-75,401 LUT 削減**
- **Slice Registers**: **7,946** (利用率 1.95%) ← 修正前推定 140,965 FF から **-133,019 FF 削減**
- **Block RAM**: **RAMB36E1: 28 個, RAMB18E1: 4 個**（正常に BRAM 推論完了）
- **動作周波数・タイミング**:
  - クロック周期制約: 5.000 ns (200.0 MHz)
  - WNS (Setup): **-0.105 ns** (実力値 $T_{min} = 5.105\text{ ns} \implies \mathbf{195.9\text{ MHz}}$)
  - 違反エンドポイント数: わずか 2 / 16,960 件（配置配線時のクロックバッファ挿入および物理最適化で容易に解消可能なレベル）

### 6.2 KC705 全体収容見込みの更新
修正前の全体合成（276,848 LUTs, 135.8%）から、L2 キャッシュの BRAM 化による削減分（-75,401 LUTs）を反映すると：
$$\text{全体予想 LUT} \approx 276,848 - 75,401 = \mathbf{201,447\text{ LUTs}}\quad (\mathbf{98.8\%})$$
さらに、`CONFIG_MC_L2_CACHE_KB = 0` または 8 KiB への縮退時には **186,000 〜 192,000 LUTs (91 〜 94%)** となり、**KC705 への収容（203,800 LUTs 枠内）が確実**となります。
